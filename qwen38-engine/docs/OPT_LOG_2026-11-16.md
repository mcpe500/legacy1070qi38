## 2. Test unit `tests/mt_dot_test.cpp` (dibangun lebih dulu, sebelum disentuh engine)

Strategi: mt_dot vs `vec_dot` ggml pada matriks acak kecil (in=512, out=8, T=5) per tipe.
Percobaan & kegagalan berurutan:

1. **Crash `malloc(): corrupted top size`** → `ggml_quantize_chunk` arg ke-6 adalah `n_per_row` (elemen),
   saya kirim byte → ggml menulis 544 elemen/baris → overflow heap. Fix: kirim `in`, bukan `wrow_bytes`.
2. **Semua tipe FAIL skala 1e34** → kesalahan bertingkat, di-debug per tipe dari yang paling sederhana:
   - dbg_q8.cpp (in=64, 1 row): Q8_0 mt == vec_dot persis → kernel dasar benar.
   - dbg2.cpp (in=512, T=5): pola salah **hanya t≥1** dan nilainya sama antar-t → saya lupa offset
     `t*arow` pada baris aktivasi ke-t. **Bug #1: stride token.** Fix: semua kernel menerima `arow`
     dan membaca `act + t*arow + b*BLOK + off`.
   - dbg3/dbg5/dbg7: formula skalar saya == vec_dot **persis** (11.7326 vs 11.7326) padahal mt_dot beda
     → bug di SIMD, bukan formula/layout. Pelacak: tipe yang pakai `hsum_ps` (Q4_K/Q5_K/IQ4_XS) gagal,
     tipe yang pakai `hsum_epi32_128` (Q6_K/Q8_0/IQ4_NL) lolos → **Bug #2: `hsum_ps` menjumlah lane 2
     dua kali** (`add_ss` terakhir menambah lagi lane yang sudah masuk via `movehl`). Fix: buang
     `add_ss(..0xAA)` final; cukup 3 langkah (lo+hi, +movehl, +lane1).
3. Hasil setelah 2 fix: **MT-DOT TEST PASS** untuk 6 tipe, worst_abs ~1.5–3.8e-5
   (distribusi angka = urutan epilog float; memang di bawah bar Poin A).

## 3. Iterasi performa (belum selesai)

- Micro-bench v1 (matriks ~48 MiB, out=17408, in=5120, T=4, `taskset -c 0-3`):
  Q4_K vec_dot 0.008 s vs **mt_dot 0.014 s (0.60×)**; IQ4_XS 0.011 vs 0.015 (0.72×).
  Diagnosis: epilog float **per unit** saya (`fmadd` 8×8/blok/token) lebih mahal daripada punya ggml yang
  mengakumulasi `scale*isum` dalam **int32** dan konversi float **sekali per blok**. Data memang menunjukkan
  vec_dot DDR-bound (4×48 MiB / 0.008 s ≈ 24 GB/s) sedangkan mt_dot compute-bound (48 MiB / 0.014 s
  ≈ 3.4 GB/s ≪ DDR) → ruang perbaikan besar.
- Micro-bench v2 (int32 epilog): masih 0.67–0.80× — spesialisasi T (akumulator register) tidak menolong.
  Baca source ggml AVX2 (`ggml-cpu/arch/x86/quants.c`) memperlihatkan 3 penyebab lain:
  1. ggml ekstrak scale/min **sekali per blok, branch-free** (trik utmp + mask: ~15 ops); saya pakai
     `get_scale_min_k4` **branchy per unit** (~120 ops/blok).
  2. ggml koreksi-min vectorized: `madd(mins, hadd(bsums))` (4 ops); saya akumulasi `mnc[t]` **skalar
     berantai** (~160 ops/blok untuk T=4) → ini killer utamanya.
  3. ggml: `madd(scale16, p16)` langsung (1 op); saya `madd(ones)`+`mullo` (2 ops).
- Micro-bench v3 (struktur ggml: epilog float-vector `acc`/`accm`, utmp scales, t-outer/u-inner dengan
  decode array di stack): Q4_K 0.99–1.11×, Q5_K 1.20–1.32× — tapi Q6_K 0.54×, IQ4_XS 0.70×.
- v4 (Q6_K + IQ4_XS dirombak mengikuti ggml): Q6_K → **maddubs pada raw unsigned 0..63** + koreksi −32
  **sekali per blok** `madd(bsums, scales)<<5` (bukan widening per token); IQ4_XS → trik `mul_add_epi8`
  (`sign_epi8` + `maddubs`, tanpa widening).
  Hasil (2 run, `taskset -c 0-3`, matriks 48 MiB):

  | tipe | T=3 | T=4 | catatan |
  |---|---|---|---|
  | Q4_K | 0.99× | 1.07–1.11× | parity–menang |
  | Q5_K | 1.20–1.30× | 1.31–1.35× | |
  | Q6_K | 1.29–1.32× | 1.34–1.35× | |
  | IQ4_XS | 1.08–1.21× | 1.21–1.33× | |

  Bug yang tertangkap di iterasi ini: (a) `hsum_epi32_256` hilang saat rewrite → build gagal; (b) array
  `acc[NT]` berukuran 1 di path generic → stack overflow, semua tipe FAIL; (c) `madd_epi16(sv, p32)` pada
  IQ4_XS (p32 = lane int32, madd butuh int16) → `mullo_epi32`; (d) `q4raw[4]` padahal j-loop menulis 0..5 →
  stack corrupt, Q6_K FAIL → diganti `q4raw[8]`.
