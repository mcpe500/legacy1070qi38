## (1) Sapuan thread: apakah CPU yang menahan?

`tools/bench27b/cpu_sweep.py`: `llama-bench -p 0 -n 64 -r 3 -t T`; pemakaian CPU proses dibaca dari `/proc/<pid>/stat` tiap detik, 5 detik pertama (pemuatan) dibuang.

UD-IQ4_XS, `-ngl 36` (28 layer di CPU, 5.46 GiB bobot layer + `output.weight` 0.81 GiB):

| `-t` | tg tok/s | core terpakai (median) | CPU sistem sibuk |
|---:|---:|---:|---:|
| 2 | 1.40 | 1.91 | 18.7% |
| 3 | 1.90 | 2.81 | 34.0% |
| 4 | **2.32** | 3.69 | 43.8% |
| 6 | 2.29 | 5.50 | 64.1% |
| 8 | 2.21 | 7.25 | 84.3% |

UD-Q4_K_M, `-ngl 32` (32 layer di CPU, 6.96 GiB + `output.weight` 0.97 GiB):

| `-t` | tg tok/s | core terpakai (p90) |
|---:|---:|---:|
| 2 | 1.64 | 1.94 |
| 3 | 2.18 | 2.76 |
| 4 | **2.58** | 3.62 |

Tafsiran (hitungan dari angka di atas, bukan pengukuran langsung bandwidth):
- Sampai 4 thread TPS naik hampir linear dengan jumlah core (1.40 → 2.32, 1.66x untuk 2x thread) dan setiap thread sibuk penuh. Di atas 4 thread (SMT) TPS turun. Jadi pada 2-4 thread **CPU (komputasi)** menahan, dan 4 core fisik adalah batasnya.
- Byte yang dibaca CPU per token: IQ4_XS ≈ 6.27 GiB x 2.32 = **15.6 GB/s**; Q4_K_M ≈ 7.93 GiB x 2.58 = **22.0 GB/s**. Q4_K_M membaca 41% lebih banyak byte per detik dari RAM dengan core yang sama, jadi IQ4_XS tidak dibatasi bandwidth RAM; dequant IQ4_XS lebih mahal per byte (OQ-015 terjawab untuk 27B: ya, IQ memperlambat di CPU ini).
- 22.0 GB/s di atas batas bawah bandwidth baca 18.4 GB/s (C-34) dan di atas puncak single channel DDR4-2933 (23.4 GB/s) hanya tipis; Q4_K_M kemungkinan sudah dekat batas RAM.

## (3) `--override-tensor`: semua layer ke GPU, FFN sebagian ke CPU

`tools/bench27b/ot_sweep.sh`: `-ngl 99 -ot "blk\.(k..64)\.ffn_(up|down|gate)\.weight=CPU"`, jadi attention, DeltaNet, embedding output, dan FFN layer 0..k-1 di GPU; FFN layer k..64 di CPU. FFN = 9.26 GiB dari 13.46 GiB bobot layer Q4_K_M.

| FFN di GPU (layer) | pp128 tok/s | tg32 tok/s |
|---:|---:|---:|
| 0 | 9.85 | 2.25 |
| 4 | 9.51 | 2.31 |
| 7 | 10.43 | 2.41 |
| 9 | 11.07 | 2.47 |
| 11 | 11.31 | 2.39 |
| 13 | 11.45 | 2.59 |
| 15 | 11.93 | **2.77** |

| 17 | 12.37 | **2.85** |
| 18, 19, 21 | CUDA OOM | - |

Q4_0 dengan override yang sama: k=15 2.43, k=17 **2.51**, k=18 OOM.

Hasil terbaik malam ini: **UD-Q4_K_M, `-ngl 99 -ot "blk\.(17..64)\.ffn_(up|down|gate)\.weight=CPU" -t 4`: 2.85 tok/s generasi, 12.37 tok/s prompt** (ctx bench 128+32, KV f16). Dibanding `-ngl 32` tanpa override (2.60): **+9.6%**. Yang berubah: semua attention dan DeltaNet ada di GPU, hanya FFN (69% bobot layer) yang dibaca CPU. Dugaan penyebab percepatan (belum diukur): CPU tidak lagi menghitung attention/DeltaNet untuk layer di RAM, dan aktivasi pindah GPU<->CPU per layer FFN, bukan per blok layer.

Catatan: VRAM habis pada k=18; dengan konteks besar atau MTP, k harus lebih kecil.

## (4) FlashAttention dan RAM pada konfigurasi terbaik

UD-Q4_K_M, `-ngl 99 -ot` FFN 17..64 ke CPU, `-t 4`, `llama-bench -p 128 -n 32 -r 2`:

| `-fa` | pp128 tok/s | tg32 tok/s |
|---|---:|---:|
| 1 (on) | 12.01 | 2.59 |
| 0 (off) | 12.38 | **2.84** |
| auto (bawaan, baris k=17 di atas) | 12.37 | 2.85 |

OQ-017: FA bawaan llama.cpp utama jalan di Pascal, tetapi pada ctx pendek **lebih lambat** (-9%). Nilai bawaan `auto` memberi angka yang sama dengan off. KV terkuantisasi (q8_0, iso3) butuh FA, jadi di sana FA tetap aktif.

`hw sample --count 420` selama dua bench itu: RAM tersedia terendah **14.12 GiB** dari 15.53 GiB, swap dari 0.724 GiB (sebelum) ke puncak **0.899 GiB (+0.175 GiB)**, VRAM puncak 8043 MiB, tanpa throttle. Bobot dibaca via mmap (page cache), jadi RAM anonim yang dipakai proses hanya ±1.4 GiB. Kenaikan swap kecil itu kemungkinan halaman proses lain yang terdorong keluar oleh page cache model; belum dibuktikan.
